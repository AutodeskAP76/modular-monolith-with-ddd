Inside every *Startup.Initialize

The same four steps repeat for each module, which is what keeps the modules isolated from each other (ADR 0016: one IoC container per module).

02

Async messaging: outbox, inbox & internal commands

How two modules exchange messages reliably, shown with one use case: a new user signs up. The Registrations module stores the new UserRegistration in its own schema. The Meetings module has its own separate Member table and must get a matching member, but Registrations never writes to Meetings' tables and Meetings is never called directly. Instead, Registrations publishes NewUserRegisteredIntegrationEvent and Meetings reacts to it by creating the Member (CreateMemberCommand) a moment later. If Meetings is slow or fails, the sign-up itself is not affected. Every hop is written to a table in the module's own schema of the shared SQL Server database (blue cards) and picked up later by a Quartz job, so nothing is lost if the process stops between two steps. The bus is the only step that does not touch the database. The Quartz jobs are started by QuartzStartup.Initialize, and the subscription in Meetings is created by EventsBusStartup.Initialize (section 01).

IEventsBus

InMemoryEventBus (singleton)

  • One instance shared by all modules in the process (ADR 0015).
  • Each module gets an InMemoryEventBusClient, which forwards to this instance.
  • Delivery is synchronous and not durable: the bus only calls the subscribed handlers. Durability comes from the inbox on the receiving side.
  • Swapping it for a real broker only requires a new IEventsBus implementation.

Processing/InternalCommands/*

Why three tables instead of calling the handler directly

Each table separates one step into its own transaction, so a failure in one step doesn't undo or block the others.

out

Outbox

sending side

Solves the dual-write problem: the data change and the "event to publish" are committed atomically. If the process dies after the commit, the job still finds the row and publishes it.

in

Inbox

receiving side

The in-memory bus is not durable, so the receiver stores the event immediately and processes it later. A failing handler never blocks the publishing module.

cmd

Internal commands

a module talking to itself

Work that must happen later in its own transaction: reacting to an inbox event, sending an email, or recurring work. It is also what keeps one handler from changing two aggregates in one transaction.

!

Guarantees

read before relying on it

At-least-once, in order of OccurredOn. Outbox and inbox rows are marked processed only after they were handled, so a crash in between causes a second run and handlers should be safe to repeat. Each module polls its own tables with its own Quartz scheduler.

Layered architecture overview

The main building blocks of the solution, from the client down to the database. A request enters through the API, crosses a module facade into one of the five business modules and reaches that module's own schema in the database. Each module also runs its own job scheduler in the background. Modules never call each other directly: they talk through the in-memory event bus, using the outbox / inbox / internal-commands pattern from section 02. Details of each part are in sections 01 and 02.
